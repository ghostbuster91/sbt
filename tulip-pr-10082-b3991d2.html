[2.x] fix: Fix build load failing on a symlink loop under the base directory

https://github.com/sbt/sbt/pull/10082

Original PR description

Written by the PR author — not part of Tulip's analysis below.

Problem: The test digest scope converts the project base directory with FileConverter.toVirtualFile, which materializes a directory by listing it recursively. The walk follows symlinks, so a self-referencing link anywhere under the base directory, such as the nixpkgs flake input that direnv places in .direnv, fails the load with "Too many levels of symbolic links".

Solution: Use toVirtualFileRef, which derives the same rooted id from the path alone and touches no files.

What this does

Loading a build hashed the project's base directory into the test-digest "scope" key by calling FileConverter.toVirtualFile(base). Only the resulting .id string was ever used, but building a VirtualFile for a directory touches the filesystem and walks the tree. If any symlink under the base directory points back at one of its own parents — e.g. the nixpkgs flake input that direnv drops into .direnv — that walk never terminates and the load dies with "Too many levels of symbolic links".

The fix is one call: toVirtualFileRef, which builds the same rooted id (${BASE}/...) from the path string alone and reads nothing from disk. The same file/directory handling already exists elsewhere — SemanticdbPlugin.scala:79 and :85 use toVirtualFileRef(dir).id for exactly this reason, and reserve toVirtualFile for where a real VirtualFile value is needed.

The one-line fix

definedTestDigestTask computes a scope digest from (project id, base directory id, configuration name, platform). Only the base-directory conversion changes; the surrounding tuple and the hashing are untouched.

main/src/main/scala/sbt/internal/IncrementalTest.scala — base 89-89, head 89-89 (1 line)
⋯ 88 lines
89- fileConverter.value.toVirtualFile(project.base.toPath).id,89+ fileConverter.value.toVirtualFileRef(project.base.toPath).id,
⋯ 315 lines

Two things worth a reviewer's eye:

  • Do the two ids match? If toVirtualFileRef produced a different id than toVirtualFile for the same directory, every cached test digest would be invalidated once (annoying, not wrong). Both go through the same root-path mapping in zinc's MappedFileConverter, so they should agree — I couldn't read the zinc source from this checkout to confirm it, so it's worth a glance if you know that code.
  • The scope value is computed before testNames is consumed, so this line runs even in a project with no tests. That's what lets the new test be source-free.

Tests

A single scripted (integration) test, tests/symlink-loop-base. It doesn't assert on digest values at all — it just checks that the build loads and the task runs where it previously crashed.

The test script is short but the ordering matters: the loop must exist before the build loads, because the digest scope is a settings node, so the test first runs a task to create the symlink, then reloads, then runs the task. The comments also record why there are no $ exists / $ absent assertions — scripted's own file commands walk the base directory recursively and would trip over the same loop.

sbt-app/src/sbt-test/tests/symlink-loop-base/test — head 1-6 (6 lines)
1+# flake-inputs/self -> flake-inputs, as direnv's .direnv layout links the nixpkgs flake input.
2+# The test digest scope is a settings node, so the loop has to be there before the build loads.
3+# No $ exists / $ absent here: scripted's file commands walk the base directory recursively.
4+> skipWindows createSymlinkLoop
5+> skipWindows reload
6+> skipWindows Test/definedTestDigests

The build.sbt provides the two pieces that script needs: a createSymlinkLoop task that makes flake-inputs/self -> flake-inputs (and asserts the link really points back at its parent, so a silently-failed symlink can't make the test pass vacuously), and a skipWindows command that swallows the rest of the line on Windows, where creating symlinks needs extra privileges. It follows the existing watch/symlinks test, which sets up symlinks the same way.

sbt-app/src/sbt-test/tests/symlink-loop-base/build.sbt — head 1-19 (19 lines)
1+import java.nio.file.Files
2+
3+scalaVersion := "3.9.0"
4+
5+Global / localCacheDirectory := baseDirectory.value / "diskcache"
6+
7+@transient
8+val createSymlinkLoop = taskKey[Unit]("create a self-referencing symlink under the base directory")
9+createSymlinkLoop := {
10+ val dir = Files.createDirectories(baseDirectory.value.toPath / "flake-inputs")
11+ val link = dir / "self"
12+ Files.deleteIfExists(link)
13+ Files.createSymbolicLink(link, dir)
14+ assert(Files.isSameFile(link, dir), s"$link does not point back to $dir")
15+}
16+
17+commands += Command.single("skipWindows") { (state, command) =>
18+ if (scala.util.Properties.isWin) state else command :: state
19+}

Because every line is wrapped in skipWindows, the test is a complete no-op on Windows — it passes without checking anything there. That's consistent with the existing symlink test, just worth knowing.
